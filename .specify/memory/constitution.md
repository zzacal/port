# Gallery Constitution

## Core Principles

### I. Single Owner, Claimed Once

The site has exactly one administrator: the owner.

1. Ownership MUST be established by the first successful Google OIDC sign-in initiated from
   `/admin` on an unclaimed site. Claiming MUST be atomic — when two sign-ins race, exactly one
   becomes owner and the other is refused.
2. Ownership MUST be bound to the Google account's immutable subject identifier, never to an
   email address.
3. After the claim, every other identity MUST be refused admin access and MUST NOT receive an
   authenticated session.
4. Ownership MUST NOT be transferable or resettable through any web request. Recovery is an
   out-of-band operator action (server-side command or direct datastore change) only.
5. The claim event MUST be logged with identity, client IP, and timestamp.
6. All admin state-changing requests MUST be protected against cross-site request forgery.

Rationale: a personal gallery needs no user management; a claim-once model removes the entire
account-administration surface. The unclaimed window between deploy and first login is an
accepted, documented risk that design MAY close with an optional claim token.

### II. Anonymous Public Viewing, Owner-Controlled Visibility

1. Visitors MUST NOT need an account, cookie consent, or sign-in to view anything public.
2. Every gallery is either public or private. Public galleries appear on the home page.
   Private galleries MUST NOT appear on the home page, in any public listing, feed, or sitemap,
   and their pages MUST be marked non-indexable — but MUST remain reachable by direct link.
   A listing served from an edge cache MAY show a gallery for up to the cache lifetime after it
   is made private; visibility changes MUST trigger a purge, best effort.
3. Because private means "unlisted", gallery and image addresses MUST NOT be guessable from a
   gallery's title or from sequential identifiers.
4. Changing a gallery's title MUST NOT break links already shared.
5. Only the owner decides what is visible; nothing becomes public as a side effect of upload,
   tagging, or editing.

Rationale: private doubles as draft and as share-by-link. Private means unlisted, not secret:
it is not access control, and nothing private-but-sensitive belongs on this site. Opaque ids are
kept because they are what make links survive renames.

### III. Published Images Leak Nothing

1. Uploaded files are the owner's edited exports and are the master copies. Masters MUST be
   stored privately and MUST NOT be served to visitors by any route.
2. Visitors MUST only receive derivatives that were generated by the owner's authenticated
   admin client and accepted by server-side validation (rules 5–7). No uploaded file reaches a
   public location without passing that validation.
3. Derivatives MUST have location (GPS) data and all other embedded metadata removed. Camera
   metadata shown to visitors (camera, lens, focal length, aperture, shutter speed, ISO) MUST
   come from an explicit allowlist extracted at upload, never from passing the file through.
4. Orientation MUST be applied to pixels before metadata is stripped.
5. The server MUST treat every uploaded derivative as untrusted and validate it before it is
   accepted. Validation checks that the format is on the allowed list (AVIF or WebP), that the
   decoded header dimensions match the declared ladder width and the master's aspect ratio, and
   that there are no embedded metadata segments of any kind (EXIF, XMP, IPTC, ICC beyond a
   standard color profile, comments, or embedded thumbnails). Validation MUST parse the file
   structure; trusting the client's declared values is not validation.
6. When any derivative of an image fails validation, the whole image MUST be rejected and nothing
   from it stored in a public location.
7. The camera-metadata allowlist (rule 3) MUST be extracted by the server from the master. Values
   reported by the client MUST NOT be used.
8. The origin server MUST NOT decode or encode image pixels. It parses only headers and metadata
   structures, which keeps image work off the fixed-cost host (Principle VIII).

Rationale: photo exports routinely carry home location and serial numbers; an allowlist is the
only approach that stays safe as camera vendors add fields. Since 2.0.0 derivatives are made in
the owner's browser, so rules 5–7 are the entire remaining protection against leaking metadata.
They are blocking acceptance criteria, never follow-up work. A test MUST prove that a derivative
with embedded GPS is rejected.

### IV. Performance: Measured and Perceived

The site MUST feel instant. Work is moved to upload time and to the moment before the visitor
asks for it, so the visitor never waits on it at view time.

Measurement

1. Every HTTP request MUST emit a structured log event with route, status, and duration.
2. Every performance-sensitive operation (image decode, EXIF read, each derivative encode,
   each storage put/get, each datastore query on a public page, each edge purge or warm) MUST
   emit a named structured timing event with duration and outcome. Operations that run in the
   owner's admin client (decode, orientation, each derivative encode) MUST report their timings
   with the upload, and the server MUST log them as named timing events, so they too are
   verifiable from server logs alone.
3. Public pages MUST expose server timing to the browser (`Server-Timing`).
4. Every success criterion with a time bound MUST be verifiable from logs alone, without
   manual stopwatch timing. Instrumentation ships with the feature, never as follow-up.
5. Perceived-performance rules below MUST each have a verification method in the plan
   (served markup/header assertion, or real-browser measurement where the effect is visual).

Upload-time precomputation (nothing is resized, encoded, or analyzed at view time)

6. Each image MUST get a width ladder of derivatives, produced at upload time in the owner's
   admin client (Principle III.2): baseline widths 320, 640, 960, 1280, 1920, and 2560, never
   upscaled past the source, encoded as AVIF with a WebP fallback, chosen via
   `<picture>`, `srcset`, and `sizes` so every view gets the smallest sufficient file.
7. Each image MUST get a placeholder computed at upload (dominant color and a tiny blurred
   preview) stored with the image record and inlined in the page, so every image slot paints a
   preview with no extra request and no JavaScript.
8. Pixel dimensions and aspect ratio MUST be stored at upload and emitted in markup so the
   layout is final at first paint (no image-caused layout shift).
9. Gallery cards (cover derivative, placeholder, dimensions, image count) MUST be
   denormalized onto the gallery so the home page is a single datastore read.
10. Publishing or editing a public gallery MUST warm the edge cache for its pages and the
    derivatives those pages reference, and tiered edge caching MUST be enabled.

Predictive loading (fetch before the click)

11. Public pages MUST declare Speculation Rules that prerender (or at minimum prefetch) gallery
    and image links on hover/press intent.
12. Hovering or touching a thumbnail MUST begin loading the image the destination view will
    show, as progressive enhancement for browsers without Speculation Rules.
13. The solo view MUST prefetch the previous and next images of the gallery after the current
    image has loaded.
14. Speculative and predictive fetches (rules 11–13) MUST be suppressed when the browser signals
    Save-Data.

Instant rendering

15. The solo view MUST paint the already-cached gallery thumbnail at full size immediately and
    reveal the sharp image over it when decoded.
16. Navigation between grid and solo view MUST use cross-document View Transitions so the
    thumbnail visibly becomes the solo image (and back); unsupported browsers navigate
    normally.
17. The primary image of each page (solo image; first row of covers or thumbnails) MUST be
    loaded with high fetch priority and eagerly; all other images lazily with async decoding.

Delivery

18. Anonymous HTML for public pages MUST be cacheable at the edge and MUST bypass the edge cache
    whenever the owner session is present. Content changes MUST purge affected pages; cached
    HTML MUST carry a bounded lifetime so a failed purge self-heals.
19. The origin MUST send Early Hints (via the edge) for critical CSS and the primary image.
20. Public pages MUST be eligible for the back/forward cache: no `unload` handlers and no
    `no-store` on anonymous responses.
21. Images and static assets MUST use content-addressed URLs served with one-year immutable
    caching; the app MUST run Always On with origin output caching for public pages.
22. Public pages MUST NOT ship a client-side framework; critical CSS is inlined and fonts are
    system fonts or a single self-hosted variable font.

Rationale: the product is a photo viewer; speed, real and perceived, is the feature.

### V. Minimal Scope, Minimal Dependencies

1. Features MUST trace to an accepted spec; no speculative capabilities (comments, likes,
   visitor search, multi-user, analytics) without a spec amendment.
2. Built-in framework capabilities MUST be preferred. Every third-party package MUST be
   justified in the plan against a specific requirement.
3. Public pages MUST work with JavaScript disabled; scripting is progressive enhancement.
   Admin pages MAY require it.

### VI. Official CLIs for Scaffolding

Projects, solutions, package references, and generated configuration MUST be created with the
official CLIs (`dotnet new`, `dotnet sln add`, `dotnet add package`, `az`, `wrangler`, etc.).
Plans, tasks, and quickstarts MUST express scaffolding as CLI commands, never as hand-written
project or manifest file contents.

### VII. Design Before Code

1. The first feature MUST be an end-to-end architecture and stack design that produces
   documents only — no application source, project files, or infrastructure changes.
2. The accepted design is the source of truth for later features. A later plan that deviates
   from it MUST say so in its Constitution Check and update the design document in the same
   feature.
3. Each design decision MUST be recorded with rationale, alternatives rejected, and pivot cost.

Rationale: hosting, TLS, storage, and identity choices interlock; deciding them piecemeal
inside feature plans produces contradictions that are expensive to unwind.

### VIII. Fixed Cost Ceiling

1. Recurring fixed hosting cost MUST NOT exceed one Azure App Service Basic B1 (Linux) plan.
   Every other component MUST use a free tier or free offering unless an amendment raises
   the ceiling.
2. TLS certificates MUST be free (Cloudflare Universal SSL at the edge; Cloudflare Origin CA
   to the origin). No paid certificate.
3. Designs MUST identify each metered cost (egress, operations, storage) and its free-tier
   limit.

## Platform Constraints

These are binding inputs to every plan:

- Application: .NET 10 minimal APIs, server-rendered HTML; htmx and web components for admin
  interactivity.
- Hosting: Azure App Service (Linux, B1). Origin MUST accept traffic only from Cloudflare.
- Edge: Cloudflare DNS, proxy, cache, and TLS in "Full (strict)" mode. Never "Flexible".
- Identity: Google OIDC, cookie session.
- Data: MongoDB (Atlas free tier, same region as the app).
- Image storage: S3-compatible object storage (Cloudflare R2 by default) behind a storage
  abstraction, with a public derivatives location and a private masters location.
- The app MUST honor forwarded headers from Cloudflare (scheme, client IP via
  `CF-Connecting-IP`) so generated URLs and audit logs are correct.

## Development Workflow

- Work flows through spec-kit: specify → clarify → plan → tasks → analyze → implement.
- Specs stay technology-agnostic; stack choices are planning inputs recorded in Assumptions.
- Plans include a Constitution Check table (principle → PASS / justified N/A / deviation).
- Implementation tasks MUST be specific enough (files, dependencies, acceptance criteria) for a
  lower-cost executor; design decisions are escalated, never made by executors.
- Build and test gates are run independently before work is accepted; existing tests MUST pass
  unmodified unless a requirement change is stated.
- Integration tests run against real Mongo and S3-compatible storage in containers, and every
  feature ends with a live-server walkthrough.
- Each feature keeps a `decisions.md` log (decision, rationale, pivot cost).

## Governance

- This constitution supersedes conflicting practice, specs, and plans.
- Amendments are made via `/speckit-constitution`, update the Sync Impact Report, and MUST land
  before any `/speckit-plan` that depends on them.
- Versioning: MAJOR when a guarantee is removed or redefined; MINOR when a principle or section
  is added or materially expanded; PATCH for wording that does not change a guarantee.
- When an amendment removes a guarantee, prior specs that relied on it MUST be annotated in
  place, not silently edited.
- Every plan and analyze pass verifies compliance and cites principles by number.
