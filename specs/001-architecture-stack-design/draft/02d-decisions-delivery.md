### D-15: Public Page Rendering
**Area**: public-rendering
**Status**: given
**Choice**: Public pages are server-rendered HTML with no client-side framework. Critical CSS is inlined; system fonts are used so no web-font request is made. The .NET 10 minimal-API host uses the built-in output cache for anonymous public pages. Images are served with a `<picture>` element listing the AVIF source first, then WebP, then `<img>`, with `srcset` and `sizes` so every viewport gets the smallest sufficient derivative. Every `<img>` carries the stored width and height. The solo view paints the gallery thumbnail, already in the browser cache, at full size as the image's initial layer and reveals the sharp `<picture>` over it once decoded; this is CSS layering, so it needs no JavaScript. The home page renders from the denormalized `site.homeCards` in one datastore read. Pages work with JavaScript disabled; scripted behaviour on public pages is progressive enhancement only.
**Rationale**: Constitution IV.8 requires dimensions in markup, IV.15 requires the thumbnail-first paint, and IV.9 requires a single home-page read. Constitution IV.22 prohibits shipping a client-side framework and mandates inlined critical CSS and system fonts. Constitution V.3 mandates that public pages work without JavaScript. Constitution IV.21 mandates origin output caching for public pages and one-year immutable caching for content-addressed assets. The `<picture>` element with AVIF-first ordering satisfies IV.6's format ladder (research R-10; [wp Q6]).
**Alternatives**: React or a similar SPA framework was rejected by Constitution IV.22 and V.3 (adds a dependency, the page fails without JS, and IV.22 prohibits it). Server-side image transcoding at view time was rejected by Constitution III.8 (origin MUST NOT decode pixels) and the IV precomputation model. An external web-font CDN was rejected by Constitution IV.22 (system fonts are the required default; a single self-hosted variable font is the allowed exception).
**Pivot cost**: medium: adding a client-side framework after launch requires replacing every server-rendered template and re-verifying compliance with Constitution IV.22 and V.3; removing it again would be equally disruptive.

### D-16: Edge Caching and Purge
**Area**: edge-cache
**Status**: chosen
**Choice**: Anonymous HTML responses for public pages are cached at the Cloudflare edge with a 1-day TTL. The cache is bypassed when the owner session cookie is present. On a content change, affected pages are purged by URL (limit: 800 URLs/s, 100 URLs per API call). Images are served on `img.<domain>`, the R2 custom domain of the `public` bucket (D-19), with a 1-year edge TTL matching each object's `Cache-Control: public, max-age=31536000, immutable` metadata. Derivative URLs on `img.<domain>` are purged by URL like pages. Smart Tiered Cache is enabled, which puts one upper tier next to the bucket [st Q2]. Public pages and their referenced derivatives are warmed after each purge.
**Rationale**: A 1-day HTML TTL bounds the staleness window when a purge fails, satisfying IV.18's self-healing requirement. URL purge is the most precise and fastest purge available on the Free plan (research R-01; [cf Q1]). An R2 custom domain is part of the zone, so the zone's cache, cache rules, and URL purge apply to images with no proxy or Worker (research R-04; [st Q2]; decisions #15, #34). Tiered Cache reduces origin pull frequency ([cf Q2]).
**Alternatives**: Azure Front Door was rejected because it costs about $35/month, violating the Constitution VIII.1 cap (research R-04). Tag and prefix purge were rejected because the Free plan rate-limits them to 5 requests/min, which is too slow for a batch of page purges ([cf Q1]). Cache Reserve was rejected as paid-only ([cf Q1]). Serving images from the R2 S3 endpoint or an r2.dev URL was rejected: neither is cached, and III.9 forbids the development URL.
**Pivot cost**: low: adjusting TTL values and purge strategy is Cloudflare dashboard and Cache Rules configuration; image URLs do not depend on the storage service behind `img.<domain>` (decisions #15).

### D-17: Predictive Loading and View Transitions
**Area**: predictive-loading
**Status**: given
**Choice**: An inline Speculation Rules script prerenders gallery and image links at `eagerness: moderate`. A hover/touch script (~20 lines) adds a `<link rel=preload>` for the destination image's `srcset` on `pointerenter`/`touchstart`. The solo view prefetches the previous and next images after the `load` event. Both scripts check `navigator.connection?.saveData` and skip when Save-Data is true; Chromium also suppresses prerender automatically under Battery Saver. Cross-document View Transitions use `@view-transition {navigation:auto}` with `view-transition-name: img-{id}` on source and destination pages; unsupported browsers navigate normally. The LCP image gets `fetchpriority=high`; all others get `loading=lazy decoding=async`. Anonymous responses carry no `no-store` and pages have no `unload` handlers, keeping them bfcache-eligible. Early Hints are sent via the Cloudflare edge from the origin's `Link: rel=preload` headers; extension-free paths qualify ([cf Q3]; [wp Q8]).
**Rationale**: Constitution IV.11 mandates Speculation Rules for gallery and image links. Constitution IV.12 mandates hover/touch preload of the destination image. Constitution IV.13 mandates solo-view prefetch of previous and next images. Constitution IV.14 mandates Save-Data suppression. Constitution IV.16 mandates cross-document View Transitions with graceful fallback. Constitution IV.17 mandates high fetch priority on the primary image and lazy loading on others. Constitution IV.19 mandates Early Hints. Constitution IV.20 mandates bfcache eligibility. All mechanisms are confirmed available on the chosen stack (research R-10; [wp Q1–Q5, Q8]).
**Alternatives**: A JavaScript-only prefetch library without Speculation Rules was rejected because Speculation Rules add full prerendering at no extra cost and Chromium handles the Save-Data guard automatically (IV.11). Disabling View Transitions was rejected because Constitution IV.16 mandates them where supported. Omitting the Save-Data guard was rejected because Constitution IV.14 requires it. Skipping Early Hints was rejected because Constitution IV.19 requires them; the Cloudflare edge generates them from `Link` headers with no origin change needed ([cf Q3]).
**Pivot cost**: low: all features are progressive enhancement; adjusting or removing them requires changes to inline scripts and CSS only, with no data-model impact.

### D-18: Metered Cost Cap
**Area**: other
**Status**: given
**Choice**: Metered spend on everything beyond the fixed B1 plan is capped at $10/month by governance: exceeding it requires a constitution amendment. An Azure budget on the subscription notifies the owner at $7/month and again at $10/month; an Azure budget sends alerts and does not stop resources. The Application Insights daily ingestion cap of 150 MB is the one configured hard limit, because it is the only metered service in this design that offers one (Constitution VIII.4). The B1 plan is the fixed cost.
**Rationale**: Constitution VIII.1 requires that metered spend not exceed $10/month and that a budget alert fire at $7/month. Constitution VIII.4 requires that every metered service offering a hard spending limit have one configured inside the VIII.1 cap. Application Insights offers a daily ingestion cap; 150 MB/day keeps monthly ingestion well inside the 5 GB/month free allowance at about 4.5 GB/month worst case (research R-09; decisions #6).
**Alternatives**: The owner was offered caps of $2 (alert $1.50), $5 (alert $3), $10 (alert $7), or no cap, and chose $10 with a $7 alert in the hosting interview (decisions #6). A higher daily Application Insights cap was rejected because 150 MB/day already keeps monthly ingestion inside the 5 GB free allowance (research R-09).
**Pivot cost**: low: changing the cap requires an amendment to Constitution VIII.1 and an update to the Azure budget rule; neither touches application code (decisions #6).

### D-19: Image Hostname
**Area**: other
**Status**: chosen
**Choice**: `img.<domain>` is attached to the `public` R2 bucket as an R2 custom domain in the same Cloudflare account, so image URLs are `https://img.<domain>/<hash>.<ext>`. The bucket's r2.dev development URL is disabled, and the app never emits an R2 S3 endpoint URL. A cache rule on `img.<domain>` caches everything with a 1-year edge TTL. Development and production use different public buckets, each attached to its own image hostname; the hostname is configuration.
**Rationale**: Constitution Platform Constraints (4.0.0) require that browsers fetch derivatives only through the image hostname and the Cloudflare cache, and III.9 requires the development URL to be off. A custom domain is the documented way to put an R2 bucket behind the zone's cache, WAF, and cache rules; the r2.dev URL supports none of them [st Q2, Q12]. This replaces the Azure-era Cloud Connector and Worker fallback, which existed only because Azure Blob needs its own Host header (constitution 3.0.0; decisions #5, #34).
**Alternatives**: A Worker in front of the bucket was rejected: code to maintain, and it would count every image request against the Workers free quota for no gain. The r2.dev URL was rejected by III.9 and because it is not cached [st Q2]. Serving images through the app was rejected because it puts image bytes on the origin.
**Pivot cost**: low: the hostname is a custom-domain attachment and a cache rule; image URLs do not change if the bucket behind them changes (decisions #34).

### D-20: Contact-Sheet Grid Component
**Area**: public-layout
**Status**: chosen
**Choice**: The home page (gallery cards) and the gallery page (image thumbnails) render through one shared server-side contact-sheet component, modelled on Nadav Kander's works-in-series grid (https://www.nadavkander.com/works-in-series, measured 2026-10-27). The component takes a column count for each of three viewport classes: large (≥ 1200 px), medium (600–1199 px) and small (< 600 px). Each usage sets its own counts: home is 3 / 3 / 1 and gallery is 4 / 3 / 1. Every tile is a cell of one fixed shape (4:3 landscape by default; Kander's measured box is about 1.28:1). The whole photo is fitted inside the cell without cropping, centred horizontally and vertically, so landscapes fill the width and portraits sit as a narrower image in the middle; the unused part of the cell is the page background. The `<img>` carries the stored width and height, `max-width:100%; max-height:100%`, and the inlined placeholder is an image layer positioned behind the photo, out of normal flow so it can never size the box, and inset 2% so it always sits inside the photo's area, never the empty cell (amended by feature 003, research R-03 and decision #28: originally "its own background"). The caption is the title only, one line, truncated with an ellipsis, centred under the cell: the gallery title on home, the image title in a gallery. No image counts, dates or other text. Outer margin and gap are 48 px (large), 32 px (medium) and 16 px (small), close to Kander's measured values. The `sizes` attribute and the CSS grid are both generated from the same column counts and spacing, so the browser picks the derivative for the real rendered cell width. The first row at the large column count (3 on home, 4 in a gallery) gets `fetchpriority=high` and eager loading; the rest are lazy. Every tile is a plain link and carries the `view-transition-name` from D-17. The component is pure CSS grid and needs no JavaScript.
**Rationale**: The owner picked Kander's grid from the reference board (docs/ux-research/moodboard.html) and asked for one component shared by home and gallery, with per-viewport column counts, every photo shown whole (letterboxed) and centred, and title-only captions. Fitting without cropping keeps every image whole in the grid; centring gives rows a common axis when shapes differ. Generating `sizes` from the same column config as the CSS keeps downloads matched to the layout (Constitution IV.6), stored dimensions keep the layout stable at first paint (Constitution IV.8), and pure CSS keeps public pages working without JavaScript (Constitution V.3). `imageCount` stays on GalleryCard because Constitution IV.9 requires it there, but it is not rendered (decisions #24).
**Alternatives**: A uniform crop (Kander's own treatment) was rejected by the owner: portraits lose their top and bottom in the grid. Each photo at its own shape (ragged rows or masonry) was rejected because rows stop lining up. A 3-column grid inside galleries was rejected in favour of Kander's split (3 on home, 4 in a series). Kander's "Series of N" subtitle and long per-image captions were rejected by the owner (title only). Separate home and gallery components were rejected because they would drift. Owner-editable column counts in admin were not chosen; counts are set per usage in the template, keeping admin scope minimal (Constitution V.1).
**Pivot cost**: low: column counts, breakpoints, cell ratio, spacing and caption treatment are component parameters and CSS; no stored data or URLs depend on them (decisions #24).

### D-21: Atomic Component Architecture and Template Engine
**Area**: component-architecture
**Status**: chosen
**Choice**: UI is organised by atomic design. Public components are server-rendered Razor components returned from minimal-API endpoints (`RazorComponentResult`, built into .NET 10). Interactive admin organisms are web components with htmx. Tokens (values, not components): spacing 48 / 32 / 16 px, breakpoints 1200 / 600 px, cell ratio 4:3, type scale, colours. Atoms: `Picture` (the only way an image is rendered: AVIF then WebP sources, `srcset`/`sizes`, stored width and height, inlined placeholder, fetch priority and loading mode, `view-transition-name`), `Title` (one line, ellipsis), `TextLink`, `ExifField` (one formatted value; renders nothing when empty); admin-only `Button`, `Input`, `Switch`, `SelectMark` (amended by feature 005: `TagChip` dropped, since the content model has no tags). Molecules: `Tile` (a link wrapping a `Picture` fitted and centred in a fixed cell, plus a `Title`), `MetadataBar` (row of `ExifField`s), `Pager` (previous / next `TextLink`s), `Brand`, `Nav`. Organisms: `ContactSheet` (grid of `Tile`s with per-viewport column counts; generates the grid CSS and `sizes` from the same config, D-20), `SoloViewer` (thumbnail-first layer, `Picture`, `MetadataBar`, `Pager`), `SiteHeader`; admin molecules `BatchItem`, `CoverMarker`, `DragHandle`, `SelectionBar`, `DangerConfirm`, `VisibilityToggle`; admin organisms `OwnerBar`, `SidePanel`, `UploadDropzone`, `BatchFooter`, `GalleryBuilder`, `SignInCard`, and admin grids reuse `ContactSheet` and `Tile` through optional overlay, class, and caption parameters (amended by feature 005: `TagEditor` dropped; components under `Components/Admin/`, specified in specs/005-admin-ui-components/contracts/admin-components.md). Templates: `PublicLayout` (header, inlined critical CSS, Speculation Rules, view-transition CSS, no scripts beyond D-17) and `AdminLayout` (owner bar plus optional side panel, D-23; htmx, the antiforgery header, and admin web components are added by the first admin feature with real behaviour; feature 005 ships it with no scripts). Pages: `/` is `PublicLayout` + `ContactSheet` of gallery cards (3 / 3 / 1); `/g/{id}/{slug}` is `PublicLayout` + `ContactSheet` of images (4 / 3 / 1); `/g/{id}/{slug}/{imageId}` is `PublicLayout` + `SoloViewer`; `/admin/*` is `AdminLayout` + admin organisms. There is no separate picture-link component: a linked picture exists only inside `Tile`, which owns the link, and the solo image is deliberately not a link because no larger or original file is offered (Constitution III.1). Each component's CSS lives beside it in a `.razor.css` file. The SDK's CSS isolation bundles these with selectors scoped per component, so the order between components doesn't matter. Tokens are single-sourced in C#, emitted as CSS custom properties, and placed first. Tokens plus the bundle are inlined as the critical CSS (amended by feature 003, research R-02). Inline `style` attributes are banned and a test enforces it. An unlinked `/ui/` index with one page per component renders every level and state with sample data. It is mapped in Development only until owner sign-in exists, then owner-only (amended by feature 003: originally `/styleguide`). A component is extracted only when it has a second consumer.
**Rationale**: The owner asked for atomic organisation. Routing every image through one `Picture` atom concentrates Constitution IV.6, IV.7, IV.8, IV.16 and IV.17 in one place, implemented and tested once. Razor components ship with .NET (Constitution V.2, no extra package), compose through parameters and child content, and render plain HTML, so public pages work without JavaScript (Constitution V.3) and ship no client framework (Constitution IV.22). One concatenated, inlined stylesheet satisfies IV.22's inlined critical CSS (decisions #25).
**Alternatives**: RazorSlices was rejected: it is an extra package and composes through layouts and partials rather than nested components. Razor Pages and MVC views were rejected as heavier than minimal APIs for four public routes. Web components on public pages were rejected because they need JavaScript to render (Constitution V.3, IV.22). A separate `PictureLink` molecule was rejected because `Tile` is its only consumer. Finer splitting (for example a `Cell` atom) waits for a second consumer (Constitution V.1).
**Pivot cost**: low: nothing is built yet; after implementation it becomes medium, since moving to another template engine means rewriting about 15 small components, with no impact on data, URLs or CSS (decisions #25).

### D-22: Solution and Project Layout
**Area**: solution-layout
**Status**: chosen
**Choice**: `Gallery.slnx` holds four projects, all created with `dotnet` CLI commands from the SDK's bundled templates: `src/Gallery.Web` (`web --no-https`), the single deployable app; `src/Gallery.Core` (`classlib`), pure logic that references no other project; `tests/Gallery.Core.Tests` and `tests/Gallery.Web.Tests` (`xunit`). Project references run Web → Core, Core.Tests → Core, and Web.Tests → Web and Core. The SDK is pinned in `global.json` to the latest released .NET 10 patch with `rollForward: latestPatch` (10.0.403 at acceptance). The scaffold adds no packages beyond template output. Packages (MongoDB.Driver, Azure.Storage.Blobs, Azure.Identity, Testcontainers, Playwright), local services (docker-compose with Mongo and Azurite), and browser assets each arrive with the feature that first needs them, justified in that feature's plan.
**Rationale**: Accepted from proposal P-01 by feature 002 (specs/002-local-app-scaffold). The owner restricted the scaffold to the projects themselves, with no added dependencies. Constitution VI requires CLI scaffolding. Keeping Core free of web and storage references lets the rule-heavy code, including the Principle III metadata rejection, be unit-tested without containers. Adding each dependency with its first consumer keeps every package traceable to a requirement (Constitution V.2).
**Alternatives**: Scaffolding with packages, health checks, and test containers up front was rejected by the owner. A separate Storage/Infrastructure project was rejected: two thin classes with one consumer. A Razor class library for components was rejected because there is only one app. The xUnit v3 template was deferred because it is an extra template install. A `latestFeature` SDK roll-forward was rejected because it makes builds non-reproducible.
**Pivot cost**: low: splitting a project out later is a file move plus `dotnet sln add`, and raising the SDK pin is one `global.json` value.

### D-23: Admin Layout Direction: Site with a Frame
**Area**: admin-layout
**Status**: chosen
**Choice**: Each admin page renders as the visitor sees it, with a thin owner layer on top: a slim top bar (admin page links, a View link to the public page, one filled primary action) and, where editing is needed, a right-hand panel. The admin is not a separate dashboard. Admin pages live on their own `/admin/*` routes. Each one renders through `AdminLayout` and the same public organisms (`ContactSheet`, `Tile`, `Picture`), with the same column counts and spacing as its public counterpart. Page by page:
- **Sign-in**: one "Sign in with Google" card over the home page's first cover. On an unclaimed site the card says the first sign-in claims the site, and a refused non-owner sees the same card with one sentence saying why.
- **Upload batch**: the whole page is a drop target with the JPEG-only and 20 MB limits stated before picking, and a bad file is refused on pick with its name and reason. Batch items fill a contact sheet, and each tile shows its state, with Restart and Delete on failed or interrupted tiles. A footer holds the count, progress, Discard, and the one Confirm action.
- **Library**: a contact sheet of every image, with a select circle on each tile, bulk actions opened from a selection count, and title and caption editing in the side panel.
- **Gallery list**: the home grid, with private galleries dimmed. Each card has a drag handle, a Public switch, and a View link.
- **Gallery builder**: the gallery grid with drag reorder (a ghost slot shows where the item will land) and "make cover" on each tile. The side panel holds title, description, and Public, and delete sits in a separate danger area as red text with no fill, naming the gallery.

Design for these states found no public reference and is owed by the wireframe step: claim and refusal screens, the in-browser processing and interrupted item states, keyboard reorder, the publish warning, the current-cover marker, the input saving and saved states, and image-delete confirmation (docs/ux-research/admin-moodboard.html).
**Rationale**: The owner picked direction A from the admin reference board (feature 004, docs/ux-research/admin-moodboard.html). The references were Lychee's signed-in album page and Ghost's site-with-settings-column, plus Immich's in-place cover mode and Uppy's batch footer for the details. Reusing the public organisms is what D-21 already planned for the library. It keeps admin and public from drifting and keeps the admin component count lowest (Constitution V.1). Separate `/admin/*` routes, rather than an owner layer on the public URLs, keep htmx and admin web components off public pages (Constitution IV.22, V.3). They also keep owner markup out of edge-cacheable HTML, which no longer depends on the session bypass alone (Constitution IV.18).
**Alternatives**: Direction B, a separate photo-manager-style workbench (PhotoPrism, Immich), was not chosen: it needs its own shell, and it would drift from the public look. Direction C, plain server-rendered forms with up/down reordering (GOV.UK, Primer), was not chosen: ordering a 40-image gallery with buttons is slow. It remains the no-script fallback for the file field. Rendering the owner layer on the public URLs themselves was rejected. One response would then vary by session, and a failed cache bypass could serve admin markup or scripts to visitors (Constitution IV.18, IV.22).
**Pivot cost**: low: nothing is built yet. After the admin ships it is medium: the owner layer and admin organisms would be rewritten, with no impact on data, URLs, or the public pages.

### D-24: Infrastructure as Code
**Area**: infrastructure-as-code
**Status**: chosen
**Choice**: OpenTofu (the open-source Terraform fork, installed with `brew install opentofu`, run as `tofu`) manages every Azure, Cloudflare (including R2), and MongoDB Atlas resource from one root module in `infra/`. Since constitution 4.0.0 this decision is on hold: hosting is under review and the site is built locally (docs/roadmap.md); the R2 buckets are created by hand until then. The module has no sub-modules and uses four providers: `azurerm`, `azuread` (the app registration and GitHub federated credential for D-25), `cloudflare`, and `mongodbatlas`. It has one environment, production. Files: `main.tf` (providers and backend), `azure.tf` (B1 plan and Web App with Always On, system managed identity, app settings, and custom domain; Origin CA certificate binding; access restrictions built from the `cloudflare_ip_ranges` data source; Log Analytics and Application Insights with a 150 MB daily cap; a subscription budget alerting at $7 and $10), `cloudflare.tf` (site and `img.<domain>` DNS, the `asuid` TXT record, Full (strict) TLS, Always Use HTTPS, Authenticated Origin Pulls, the Origin CA certificate, cache rules, Tiered Cache, Early Hints, the two R2 buckets with their custom domain, CORS, and lifecycle rules, a bucket-scoped R2 token, and a purge-only API token), `atlas.tf` (M0 cluster, database user, and an access list of the Web App's possible outbound IPs), `deploy.tf` (the D-25 app registration, federated credential, and role assignment), plus `variables.tf` and `outputs.tf`. Cross-provider values (hostnames, verification ids, IP ranges, the connection string, and the purge token) flow between resources inside one plan. State lives in a dedicated small storage account and `tfstate` container, created once with `az` before the first `tofu init` and locked by blob lease. Secrets are App Service app settings written by OpenTofu; there is no Key Vault. Steps with no usable API stay in a runbook (`infra/README.md`): adding the domain to Cloudflare, creating the Google OAuth client, and creating the provisioning credentials (Azure CLI login, a Cloudflare provisioning token, and Atlas API keys), which stay on the owner's machine and never reach the app. OpenTofu runs only from the owner's machine (`tofu plan`, then `tofu apply`); the D-25 pipeline never runs it.
**Rationale**: Accepted from proposal P-02 option A by the owner. The deciding factor is the cross-provider wiring: the Web App hostname and verification id feed Cloudflare DNS, Cloudflare's IP ranges feed Azure access restrictions (Constitution, Platform Constraints: origin accepts only Cloudflare), outbound IPs feed the Atlas access list, and three secrets feed app settings. One plan wires and previews all of it and detects drift when a dashboard setting is edited. OpenTofu was chosen over HashiCorp Terraform because Homebrew core no longer ships Terraform after its licence change, while OpenTofu installs with one official command and uses the same providers and language (Constitution VI). The state account is separate from the app's storage account because the app account is itself created by the plan, so it cannot hold the state for its own first apply. The budget and the ingestion cap are provisioned with the first resources because metered spend starts then (Constitution VIII.1, VIII.4).
**Alternatives**: Bicep through `az` for Azure, with a curl script for Cloudflare and the `atlas` CLI, was not chosen: native and stateless, but the cross-provider wiring becomes hand glue between three imperative scripts, Cloudflare changes cannot be previewed, and nothing re-syncs the IP ranges. Dashboards plus a checklist were not chosen: there is nothing to rebuild from or diff against. HashiCorp Terraform was not chosen only because of installation; the files are compatible. Storing state in the app's own storage account (as P-02 first proposed) was rejected because of the bootstrap order. Key Vault was rejected: metered per operation, and one more component for three secrets. Running OpenTofu in GitHub Actions (plan-only or plan-and-apply) was rejected by the owner: Cloudflare and Atlas tokens would have to be stored as GitHub secrets, and the pipeline identity would need subscription-wide rights to create role assignments. Infrastructure changes are rare enough that a local run costs little.
**Pivot cost**: low before provisioning; after, moving to another tool is a re-import of about 40 resources (about an hour), and moving to dashboards is simply deleting `infra/` and the state account.

### D-25: Deployment Pipeline
**Area**: deployment-pipeline
**Status**: chosen
**Choice**: GitHub Actions in the `zzacal/port` repository, defined in one workflow file. Every push to any branch restores, builds, and runs both test projects. Pushes to `main` then publish with `dotnet publish` and deploy to the Web App with `azure/webapps-deploy`, after the tests pass. The workflow signs in to Azure with `azure/login` using OIDC federation: OpenTofu (D-24) creates an Entra app registration with a federated credential whose subject is the `main` branch of `zzacal/port`, and a role assignment scoped to the Web App only. The three non-secret ids the login needs (client, tenant, subscription) are stored as GitHub repository variables with `gh variable set`; no credential is stored in GitHub. There is one environment and no staging slot. Integration tests that need real Mongo and Azurite run on the hosted runner, which has Docker available, when the first feature that adds them arrives.
**Rationale**: Accepted from proposal P-03 by the owner. Tests on every push catch a broken branch before the local merge into `main`, and deploying only from `main` matches the owner's workflow of merging locally and pushing. OIDC means no long-lived secret exists to leak or rotate. Scoping the role to the Web App limits what a compromised workflow can do. B1 has no deployment slots, and slots would need Standard S1, which exceeds Constitution VIII.1.
**Alternatives**: Running the workflow only on `main` was not chosen because branches would go untested until merge. Deploying from the owner's machine with `az webapp deploy` was not chosen because no test gate would stand between a commit and production. It remains the manual fallback. A publish profile or client secret in GitHub secrets was rejected in favour of OIDC.
**Pivot cost**: low: the pipeline is one workflow file plus one app registration, and switching to manual `az webapp deploy` needs no infrastructure change.
